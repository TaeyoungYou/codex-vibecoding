# 오늘의 코딩 퀘스트 — 작업 지침

이 지침은 `coding-quest-card/`와 그 하위 파일의 작업에 적용한다.

## 1. 작업 시작 시 읽을 문서

작업을 시작하기 전에 다음 문서를 확인한다.

- `prompt/context-card.md`
  - 프로젝트 목표
  - 핵심 기능
  - 구현 범위
  - 제외 범위
  - 완료 기준

- `prompt/docs-read.md`
  - Motion for React 관련 조사 내용
  - 최신 API 사용 기준

- 작업 대상 하위 경로에 별도의 `AGENTS.md` 또는 지침 파일이 있다면 함께 확인한다.

프로젝트의 구체적인 제품 요구사항은 `prompt/context-card.md`를 기준으로 한다.

---

## 2. 프로젝트 목표와 현재 상태

- 목표는 `오늘의 코딩 퀘스트` 웹앱을 실제로 구현하는 것이다.
- 현재 단계는 설계 검토 단계가 아니라 **구현 단계**다.
- `prompt/context-card.md`에 기록된 확정 사항은 구현 요구사항으로 취급한다.
- Build Prompt에서 구현을 요청하면 별도의 승인 절차 없이 현재 세션에서 실제 코드 작성과 수정을 진행한다.
- 설계 문서나 제안서를 새로 만드는 것으로 작업을 끝내지 않는다.
- 범위 내에서 필요한 구현 세부사항은 합리적으로 결정하고 계속 진행한다.

---

## 3. 판단 우선순위

작업 중 판단이 필요하면 다음 순서를 따른다.

1. 시스템 및 상위 지침
2. 사용자의 최신 명시적 요청
3. `prompt/context-card.md`
4. 이 `AGENTS.md`
5. 현재 프로젝트의 기존 구조와 코드 스타일
6. 공식 문서 및 Context7에서 확인한 최신 문서

상위 요구사항과 하위 요구사항이 충돌하면 상위 요구사항을 따른다.

---

## 4. 범위 관리

- `context-card.md`의 In Scope에 포함된 기능은 구현한다.
- Out of Scope에 포함된 기능은 구현하지 않는다.
- 사용자가 요청하지 않은 기능을 임의로 추가하지 않는다.
- 로그인, DB, AI 기능, 자동 채점, 랭킹, 서버 저장 등 범위 밖 기능을 임의로 도입하지 않는다.
- 문서에 나온 모든 Motion API를 사용하기 위해 억지로 기능을 추가하지 않는다.
- 예제 코드는 프로젝트 기능과 관련된 경우에만 사용한다.

기존 요구사항을 반복해서 사용자에게 확인하지 않는다.

다음과 같은 **작은 구현 결정은 스스로 결정한다.**

- 컴포넌트 분리
- 변수명
- 파일 배치
- 간단한 상태 구조
- spacing
- responsive breakpoint
- 작은 UX 세부사항
- 구현을 위한 내부 로직

다음과 같이 **프로젝트 범위를 크게 바꾸는 결정만 사용자 확인이 필요하다.**

- 새로운 핵심 기능 추가
- 기술 스택 전체 변경
- 백엔드 도입
- 인증 도입
- 데이터 저장 정책 변경
- 기존 사용자 흐름의 근본적인 변경

확인이 필요한 문제가 있더라도, 해당 문제와 독립적인 구현은 계속 진행한다.

---

## 5. 구현 원칙

- 먼저 현재 프로젝트 구조와 기존 코드를 확인한다.
- 기존 구현을 재사용할 수 있으면 새로 만들지 않는다.
- 필요한 범위만 수정한다.
- 불필요한 리팩터링은 하지 않는다.
- 사용자 요청과 무관한 파일은 수정하지 않는다.
- 기존 코드 스타일과 디렉터리 구조를 최대한 유지한다.
- 새로운 라이브러리는 필요한 경우에만 추가한다.
- 단순하게 해결할 수 있는 문제를 과도하게 추상화하지 않는다.
- 테스트 목적 외의 임시 코드, dead code, 사용하지 않는 파일을 남기지 않는다.

---

## 6. React 및 Motion 사용 기준

React 기반으로 구현한다.

Motion 관련 기능은 `motion` 패키지를 사용한다.

일반 React 컴포넌트와 hooks는 다음 경로에서 import한다.

```js
import { motion } from "motion/react";
```

필요한 경우 Context7과 Motion 공식 문서를 다시 확인한다.

### Motion API 사용 원칙

필요한 기능에 한해서 다음 API를 사용한다.

- `motion.div`, `motion.button` 등
- `initial`
- `animate`
- `exit`
- `transition`
- `AnimatePresence`
- `whileHover`
- `whileTap`
- `whileFocus`
- `whileInView`
- `useScroll`
- `useTransform`
- `drag`
- `dragConstraints`
- `whileDrag`
- `layoutId`
- `LayoutGroup`
- `useReducedMotion`

### Motion 관련 규칙

- deprecated 또는 제거된 API를 사용하지 않는다.
- 과거 `framer-motion` 예제를 그대로 복사하지 않는다.
- 현재 `motion/react` 기준으로 확인한다.
- `exitBeforeEnter`는 사용하지 않는다.
- 필요한 경우 `AnimatePresence`의 `mode="wait"`를 사용한다.
- 제거되는 요소에는 안정적인 `key`를 사용한다.
- `useScroll`의 ref는 실제 대상 또는 스크롤 컨테이너에 연결한다.
- MotionValue는 필요한 경우 `style`에 직접 연결한다.
- 모든 API를 보여주기 위해 불필요한 애니메이션을 추가하지 않는다.
- 애니메이션은 사용자의 행동과 상태 변화를 이해하는 데 필요한 만큼만 사용한다.

공식 문서와 Context7 내용이 다르면 최신 공식 React 문서를 우선 확인한다.

## 7. CSS 및 UI 기준

- CSS 클래스와 선택자는 BEM 형식을 따른다.

예:

```css
.quest-card {
}
.quest-card__title {
}
.quest-card__button {
}
.quest-card__button--active {
}
```

- UI는 콘텐츠 가독성을 우선한다.
- desktop과 mobile 환경 모두 정상적으로 사용 가능해야 한다.
- 불필요한 가로 스크롤이 발생하지 않도록 한다.
- hover만으로 주요 기능을 제공하지 않는다.
- 주요 조작은 keyboard와 touch에서도 사용할 수 있어야 한다.
- focus 상태를 시각적으로 확인할 수 있어야 한다.
- 애니메이션은 접근성을 고려한다.
- 사용자의 reduced motion 설정이 있는 경우 `useReducedMotion`을 고려한다.
- 샘플 데이터는 실제 데이터처럼 오해되지 않도록 한다.

---

## 8. 구현 작업 방식

Build Prompt에서 구현을 요청하면 다음 흐름으로 작업한다.

1. `AGENTS.md` 확인
2. `context-card.md` 확인
3. 현재 프로젝트 구조 확인
4. 기존 구현 상태 분석
5. 필요한 작업 범위 결정
6. 실제 코드 작성 및 수정
7. 실행
8. 기능 검증
9. 오류 수정
10. 최종 결과 보고

계획 작성 자체를 최종 결과로 취급하지 않는다.

필요한 분석은 짧게 수행하고 실제 구현으로 넘어간다.

사용자 승인을 기다리기 위해 작업을 중단하지 않는다.
이미 정의된 범위 내에서는 현재 세션에서 가능한 작업을 완료한다.

---

## 9. 검증 기준

코드 작성이 끝났다고 작업 완료로 판단하지 않는다.

가능한 경우 실제 실행을 통해 검증한다.

최소한 다음을 확인한다.

### 기능

- 핵심 기능이 정상적으로 동작하는가
- 주요 사용자 흐름이 끊기지 않는가
- 상태 변화가 예상대로 동작하는가

### Motion

- 등장 애니메이션
- 상태 변경 애니메이션
- 퇴장 애니메이션
- gesture
- scroll animation
- drag

중 실제 구현한 기능만 확인한다.

사용하지 않는 기능을 검증했다고 보고하지 않는다.

### UI

- desktop
- mobile
- keyboard
- touch

환경에서 주요 기능이 사용 가능한지 확인한다.

### 오류

- runtime error
- console error
- React warning

을 확인한다.

### 프로젝트 검사

프로젝트에 존재하는 경우 다음을 수행한다.

- build
- lint
- type check
- test

존재하지 않는 스크립트를 임의로 가정하지 않는다.

---

## 10. 구현 완료 기준

다음 조건을 만족해야 구현 완료로 본다.

- `context-card.md`의 핵심 기능이 구현됨
- 주요 사용자 흐름이 실제로 동작함
- Motion 기능이 최신 API 기준으로 구현됨
- 주요 화면이 desktop/mobile에서 깨지지 않음
- 주요 조작이 keyboard/touch에서도 사용 가능함
- 런타임 오류가 없음
- 프로젝트 build가 가능한 경우 성공함
- 구현 범위를 벗어난 기능이 추가되지 않음

---

## 11. 완료 보고

작업이 끝나면 장황한 설명 대신 다음 내용을 간단히 보고한다.

### 구현

- 구현한 기능

### 변경

- 주요 수정/추가 파일

### 검증

- 실행한 build / lint / test
- 실제 브라우저에서 확인한 사용자 흐름

### 남은 문제

- 미완료 항목
- 검증하지 못한 항목
- 실제로 확인이 필요한 문제

검증하지 않은 내용을 검증했다고 보고하지 않는다.

---

## 12. 금지 사항

다음 행동을 하지 않는다.

- 구현 요청을 받았는데 설계 문서만 작성하고 종료
- 사용자 승인을 기다린다는 이유로 범위 내 구현을 중단
- 요구하지 않은 기능 추가
- 불필요한 대규모 리팩터링
- deprecated Motion API 사용
- 오래된 `framer-motion` 예제를 검증 없이 사용
- 실제로 실행하지 않은 테스트를 성공했다고 보고
- 존재하지 않는 요구사항을 임의로 만들어 구현
