# guestbook-memory-bank 저장소 로컬 스킬 작성 계획

작성일: 2026-10-12
상태: 최신 사용자 명세를 반영한 계획. 실제 스킬과 메모리 파일은 아직 생성하지 않음.

## 1. 목적과 이번 작업 범위

Realtime Guestbook 앱의 간단한 프로젝트 메모리 뱅크를 유지하는
저장소 로컬 스킬 `guestbook-memory-bank`를 만든다.
새 세션이나 휴식 후에도 현재 상황을 이해하고 작은 작업부터 이어갈 수 있도록 돕는다.

이번 요청의 산출물은 이 계획서의 수정본이다.
아래의 생성·갱신 절차는 이후 스킬 작성 시 구현할 내용이며 이번에 실행하지 않는다.

최신 사용자 명세에 따라 기존 계획의 개인 설치안과 Cline식 파일 구성을 변경한다.

- 스킬 진입점: `.agents/skills/guestbook-memory-bank/SKILL.md`
- 프로젝트 기록: `.memory-bank/`
- 기본 문서: 사용자가 지정한 6개 파일
- 작은 작업 카드: `.memory-bank/tasks/`
- 작성 방식: 짧은 한국어 문장과 초보자가 이해할 수 있는 설명
- 작업 상태: `done`, `in progress`, `blocked`, `next`

2026-10-12 확인 시 스킬 진입점, `.memory-bank/`, `package.json`은 없다.
기존 PRD의 수정 사항과 미추적 문서는 보존한다.
스킬 생성 단계에서 파일과 Git 상태를 다시 확인한다.

## 2. 저장 위치와 최소 구성

모든 경로는 방명록 프로젝트 루트 `realtime-feed/`를 기준으로 한다.

```text
realtime-feed/
├── .agents/
│   └── skills/
│       └── guestbook-memory-bank/
│           └── SKILL.md
└── .memory-bank/
    ├── project-brief.md
    ├── active-context.md
    ├── progress.md
    ├── decision-log.md
    ├── next-actions.md
    ├── verification-log.md
    └── tasks/
        └── YYYY-MM-DD-short-task-name.md
```

스킬 지침과 간단한 기록 양식은 우선 `SKILL.md` 하나에 둔다.
별도 스크립트·패키지·템플릿 폴더·UI 메타데이터는 초기 구성에 추가하지 않는다.
작업 카드 예시 파일은 실제 작업이 있을 때만 만든다.

상위 Git 저장소나 사용자 홈에 같은 스킬을 설치하지 않는다.
다른 위치의 기존 `memory-bank/`가 발견되더라도 자동 이동·삭제·병합하지 않는다.
대상 루트는 프로젝트 지침과 PRD 경로를 확인해 정하고, 관련 없는 앱에는 쓰지 않는다.

## 3. 스킬이 적용되는 경우

`SKILL.md`의 YAML frontmatter에 정확한 이름과 다음 적용 조건을 넣는다.

1. 이 프로젝트에서 새 Codex 세션을 시작할 때
2. 휴식 후 작업을 이어갈 때
3. 작은 구현 작업을 준비할 때
4. 완료된 작업을 요약할 때
5. 프로젝트 진행 노트를 업데이트할 때

이 조건을 `description`에 명시하고 기본 자동 선택을 유지한다.
명시적인 `$guestbook-memory-bank` 호출도 지원한다.
스킬 파일은 세션 시작 훅이 아니므로 항상 자동 실행된다고 설명하지 않는다.
일반적인 기술 질문이나 다른 프로젝트의 메모리 관리로 적용 범위를 넓히지 않는다.

예정된 사용 예는 다음과 같다.

```text
$guestbook-memory-bank 이 프로젝트의 현재 상황과 다음 작업을 알려줘.
$guestbook-memory-bank 11-7 범위에서 작은 구현 작업 하나를 준비해줘.
$guestbook-memory-bank 오늘 완료한 작업과 검증 결과를 정리해줘.
```

## 4. 읽을 문서와 근거 확인

스킬 사용 시 적용 지침과 프로젝트 루트를 먼저 확인하고, 다음 파일을 존재하는 범위에서 읽는다.

- [AGENTS.md][agents]: 작업 범위, 문서 우선순위와 검증 규칙
- [DESIGN.md][design]: 시각·상호작용·반응형 기준
- [PRD/디자인 문서][prd]: 제품 목적, 요구사항과 인수 기준
- [제품 구현 계획][app-plan]: 현재 작업과 관련된 단계와 파일 책임
- `.memory-bank/`의 기본 문서 6개: 현재 맥락·진행·결정·다음 행동·검증 기록
- `.memory-bank/tasks/`의 진행 중·차단된 카드와 현재 작업에 관련된 카드

새 세션이나 작업 재개 시에는 기본 문서 6개를 읽는다.
같은 세션에서는 변경된 기록과 현재 작업의 근거를 중심으로 읽는다.
완료된 모든 작업 카드를 매번 읽거나 기준 문서 전체를 메모리에 복사하지 않는다.

없는 기준 문서는 없다고 기록한다. 파일이 없는 것을 구현 실패로 단정하지 않는다.
현재 상태는 필요한 파일과 실제 검사 결과로 확인하고, 예정된 구조를 구현된 사실로 쓰지 않는다.
메모리를 작성하려고 환경 변수 파일·인증 캐시·개인 계정 자료를 열지 않는다.

## 5. 유지할 기본 문서

| 파일 | 짧게 기록할 내용 |
| --- | --- |
| `project-brief.md` | 앱 목적, 전체 목표와 현재 11-7 범위, 기준 문서 링크 |
| `active-context.md` | 현재 초점, 진행 중 작업, 중단 지점과 차단 사유 |
| `progress.md` | 작업별 상태, 짧은 결과, 관련 카드와 검증 기록 링크 |
| `decision-log.md` | 결정일, 적용 범위, 결정·이유·출처, 제안/확정 구분 |
| `next-actions.md` | 다음 행동, 우선순위, 선행 조건과 관련 카드 |
| `verification-log.md` | 실행일, 환경, 실제 검사·결과, 실패·미검증 사항 |

각 문서에는 최종 갱신일과 필요한 근거 링크를 둔다.
긴 대화나 원시 로그 대신 한 항목에 핵심 사실과 다음 행동만 적는다.
어려운 용어는 처음 사용할 때 짧게 설명하고, 알 수 없는 값은 `미확인`으로 남긴다.

`decision-log.md`에서는 사용자 결정, 문서 기준, 작성자 제안을 구분한다.
결정이 바뀌면 이전 결정을 조용히 삭제하지 않고 새 결정과 대체 관계를 남긴다.
진행·다음 행동 문서는 현재 상황에 맞춰 정리하고 상세 내용은 작업 카드로 연결한다.

### 작업 상태와 검증 결과

| 작업 상태 | 뜻 |
| --- | --- |
| `done` | 해당 작업의 완료 조건과 필요한 검증을 충족함 |
| `in progress` | 시작했으며 아직 완료 조건을 모두 충족하지 못함 |
| `blocked` | 필요한 정보·환경·의존성 때문에 진행할 수 없음 |
| `next` | 아직 시작하지 않은 다음 작업 후보 |

상태가 `blocked`이면 원인과 해제 조건을 적는다.
검증 결과는 작업 상태와 별도로 `통과`, `실패`, `미검증`으로 기록한다.
코드 작성이나 빌드 성공만으로 실제 서비스의 동작을 `done`으로 바꾸지 않는다.
필수 검증이 남았다면 작업을 미완료로 유지하고, 환경 문제가 원인이면 차단 상태를 사용한다.

## 6. 작은 작업 카드

작은 구현 작업을 준비할 때 `.memory-bank/tasks/`에 카드 하나를 만든다.
기존 카드가 같은 작업을 다루면 새 카드를 중복 생성하지 않고 갱신한다.
파일명은 날짜와 짧은 작업명을 사용하고 같은 이름이 있으면 덮어쓰지 않는다.

카드에 다음 항목을 짧게 둔다.

- 제목과 작업 범위: 예를 들어 11-7의 샘플 데이터 화면
- 상태: 지정된 4개 값 중 하나
- 목표: 이번 작업이 끝나면 달라질 동작 한 가지
- 관련 문서와 예상 변경 파일
- 할 일과 제외할 일
- 완료 조건과 예정된 검증
- 실제 결과·실행한 검증·미검증
- 차단 사유·해제 조건 또는 다음 행동

카드는 한 번에 검토 가능한 작은 작업으로 제한한다.
카드를 작성했다는 이유만으로 앱 코드를 편집하거나 의존성을 설치하지 않는다.
계획만 요청된 경우 카드를 검토할 수 있게 제시한 뒤 구현 전환을 확인한다.
사용자가 이미 해당 구현을 명시적으로 요청했다면 같은 승인을 반복해서 요구하지 않는다.

## 7. 운영 흐름

### 시작·재개와 누락 파일 생성

1. 최신 요청, 프로젝트 루트와 적용 지침을 확인한다.
2. 기존 기준 문서와 메모리 기록을 읽고 현재 작업을 파악한다.
3. 기본 문서가 없으면 `.memory-bank/`와 없는 파일만 만든다.
4. 기존 문서·사용자 메모를 보존하며 현재 확인한 내용으로 짧게 채운다.
5. 진행 중 작업, 차단 사항과 다음 행동을 요약한다.

누락 파일 생성은 향후 스킬의 기본 동작이다.
부분 구성에서는 없는 파일만 보완한다. 명시적인 파일 변경 금지 요청이 있으면 그 요청을 우선한다.
생성 후에는 어떤 파일을 만들었고 어떤 사실이 아직 미확인인지 알린다.

### 작업 준비

1. 현재 범위와 `next-actions.md`를 확인한다.
2. 작은 작업 하나를 고르고 기존 카드를 찾거나 만든다.
3. 목표·제외 범위·변경 파일·완료 조건과 검증을 정리한다.
4. 계획만 요청되었다면 문서 준비에서 멈추고 코드 편집 전에 확인한다.

### 작업 완료·진행 노트 갱신

1. 실제 변경, 미완료 부분과 실행한 검증을 확인한다.
2. 관련 작업 카드와 `progress.md`의 상태를 맞춘다.
3. 현재 맥락과 다음 행동을 갱신하고 실행 결과는 `verification-log.md`에 남긴다.
4. 새 결정이 있을 때만 결정 기록을, 범위가 바뀔 때만 프로젝트 요약을 갱신한다.
5. 수정한 기록과 남은 차단·미검증을 보고한다.

이 흐름은 해당 작업이 요청한 범위에서 수행한다.
변경이 없는 문서를 다시 쓰거나 과거 검사를 근거 없이 반복하지 않는다.

## 8. 11-7 범위와 기존 제품 문서의 관계

현재 사용자 요청의 11-7 범위는 다음과 같다.

- 앱은 Realtime Guestbook이다.
- 샘플 방명록 데이터를 먼저 사용한다.
- 실제 Supabase 연결은 명시적으로 요청되기 전까지 범위 밖이다.
- 로그인·회원가입은 범위 밖이다. 익명 인증 연결도 자동으로 선행 작업에 넣지 않는다.

기존 PRD와 제품 구현 계획에는 전체 제품의 Supabase 연동과 익명 인증이 포함되어 있다.
메모리에는 전체 제품 목표와 현재 11-7 작업 범위를 구분해 적는다.
기존 문서에 연동 단계가 있다는 이유로 그 작업을 11-7의 다음 작업으로 자동 등록하지 않는다.
실제 연동이 요청되면 대상과 새 작업 범위를 확인한 뒤 관련 문서·결정·카드에 반영한다.

샘플은 개인 계정과 무관한 합성 데이터를 사용한다.
임시 `.superpowers/` 시안의 데이터·체험 이벤트·접근 키를 복사하지 않는다.
샘플 화면·로컬 동작 검증은 실제 저장·인증·두 세션 간 실시간 연동 검증과 구분한다.
실시간 연결이 구현·검증된 것처럼 기록하지 않는다.

이 계획 수정은 단계별 범위의 기록 방식 변경이다.
PRD와 `DESIGN.md`의 전체 제품 목표를 삭제하거나 바꾸는 작업은 포함하지 않는다.

## 9. 안전 경계

- 비밀번호, API 키, 토큰, Supabase URL 값, 개인 계정 데이터를 기록하지 않는다.
- 공개 URL·공개 키도 실제 값은 저장하지 않는다. 필요한 환경 변수는 이름과 역할만 적는다.
- 메모리 본문, 카드, 명령 예시와 검사 결과에 같은 규칙을 적용한다.
- 로그에 금지 정보가 있으면 원문을 복사하지 않고 값을 제거한 결과만 요약한다.
- 노트 저장 전에 작성할 내용에 금지 정보가 섞였는지 확인한다.
- 다른 앱·사용자 홈·전역 Codex 메모리와 설정을 수정하지 않는다.
- 스킬 사용을 DB 변경·외부 서비스 연결·배포·메시지 전송 권한으로 해석하지 않는다.
- 기존 변경과 사용자 메모를 보존하며 임의 삭제·덮어쓰기를 하지 않는다.
- 계획 요청은 계획과 기록 작성까지만 수행하고 코드 편집 전에 구현 요청을 확인한다.
- 빌드·mock·HTTP 응답·구독 로그만으로 전체 제품과 실제 연동을 검증했다고 주장하지 않는다.

## 10. 이후 스킬 작성 순서

아래 항목은 향후 실행할 작업이다.

1. 최신 요청·적용 지침·이 계획과 실제 Git 상태를 확인한다.
2. 지정 경로에 기존 스킬이 있는지 확인하고 `SKILL.md`를 생성하거나 필요한 부분을 수정한다.
3. 이름과 5개 적용 조건, 읽을 문서, 누락 파일 생성과 6개 기록의 책임을 작성한다.
4. 작업 카드 양식, 4개 상태와 검증 결과의 구분을 작성한다.
5. 11-7 범위, 금지 정보, 계획 요청의 코드 편집 경계를 작성한다.
6. 스킬 구조·Markdown·상대 링크를 검사하고 아래 시나리오를 임시 프로젝트에서 확인한다.
7. 실제 스킬 선택이나 명시 호출을 확인하고, 확인하지 못한 부분은 미검증으로 보고한다.

스킬 생성 후 실제 프로젝트의 메모리 초기화 여부는 요청 범위와 실제 사용 여부에 맞춰 보고한다.
스킬을 작성한 것만으로 기본 문서와 작업 카드까지 이미 생성됐다고 설명하지 않는다.

## 11. 검증과 완료 조건

| 시나리오 | 기대 결과 |
| --- | --- |
| 메모리가 없는 새 세션 | 기본 문서 6개 생성, 미확인 사실은 그대로 표시 |
| 일부 파일과 기존 메모가 있음 | 없는 파일만 보완, 기존 내용 보존 |
| 작은 11-7 작업 준비 | 샘플 데이터 기준 카드, 인증·실제 연동 작업 제외 |
| 계획만 요청 | 문서·카드 준비 후 코드 편집 전 확인 |
| 검사 일부만 통과 | 완료 조건·검증 결과·미완료와 차단 원인 구분 |
| 결정 변경·작업 재개 | 결정 이력 보존, 현재 작업과 다음 행동 연결 |
| 금지 정보가 섞인 입력 | 값을 노트·카드·검증 로그에 복사하지 않음 |
| 다른 프로젝트에서 호출 | 대상 확인, 관련 없는 루트에 파일 생성하지 않음 |

스킬 작성 완료 조건은 지정 경로와 이름, 5개 적용 조건, 6개 기록과 작업 카드 운영,
상태 구분·안전 경계와 구조·동작 검증 결과가 갖춰지는 것이다.
실제 세션 동작을 확인하지 못했다면 구조 검사만으로 검증 완료를 주장하지 않는다.

향후 검사 예시는 다음과 같다. 이번 계획서 수정에서 실행한 스킬 검사가 아니다.

```powershell
$creatorFolder = Join-Path $env:USERPROFILE '.codex/skills/.system/skill-creator'
$skillFolder = '.agents/skills/guestbook-memory-bank'
python (Join-Path $creatorFolder 'scripts/quick_validate.py') $skillFolder
npx.cmd --yes markdownlint-cli2 "$skillFolder/SKILL.md"
```

현재 단계에서는 수정한 계획서의 Markdown 문법과 기준 문서 상대 링크를 검사한다.
실제 스킬·메모리 생성과 앱 실행·빌드·Supabase·배포 검증은 이번 작업의 검사 대상이 아니다.

스킬 생성 후 결과는 사용자가 요청한 다음 4개 항목으로 요약한다.

1. 스킬이 적용되는 경우
2. 읽는 파일
3. 생성·갱신하는 파일
4. 따르는 안전 경계
