# 실시간 방명록 제품 요구사항 문서(PRD)

작성일: 2026-10-11
기존 설계 상태: 사용자 승인 완료(2026-10-11). 승인된 설계는 구현 계획 작성의 기준이다.
보강일: 2026-10-11. 기존 설계를 같은 파일에서 PRD 형식으로 재배치하고 사용자 스토리·인수 기준·예외 상황·리스크를 보강했다. 보강 과정에서 명확히 한 세부 동작은 설계자 보강안이며, 기존 승인 이력을 새로운 정책의 승인으로 확대하지 않는다.

연결 문서: [기존 구현 계획](../plans/2026-10-11-realtime-guestbook.md). 이 PRD가 제품 요구사항의 기준이며, 구현 계획은 작업 순서와 구체적인 구현 선택을 다룬다. 기존 계획이 참조하는 보강 전 절 번호는 마지막 대응표에서 찾을 수 있다.

## 1. Executive Summary — 제품 개요

실제 방문자가 닉네임을 정하고 글, 이미지, 직접 그린 그림을 남기는 작은 웹 앱을 만든다. 다른 방문자의 작성·수정·삭제가 새로고침 없이 보이고, 휴대폰에서도 읽기와 그림 작성이 편해야 한다. 실제 서비스로 배포하고 브라우저 두 개에서 동작을 확인하는 것이 완료 기준이다.

이전 프로젝트 상태나 과거 계획을 이어받지 않고 새로 시작한다. 현재 작업 폴더에는 제품 구현이 없으며, 사용자와 디자인을 논의하기 위한 임시 프로토타입만 있다. 프로토타입의 예시 게시물, 닉네임 저장 방식, 실시간 체험 기능은 실제 서비스의 인증·저장·동기화 구현이 아니다.

### 문제와 제안하는 해결책

방문자가 별도 계정 가입 없이 인사나 시각적인 내용을 남기고, 다른 방문자가 남긴 내용도 새로고침 없이 확인할 수 있는 공간이 필요하다. 닉네임을 입력하는 익명 인증, 글·이미지·재편집 가능한 그림을 담는 공개 피드, 작성자에게만 허용되는 수정·삭제를 하나의 작은 웹 앱으로 제공한다.

### 성공 판정

출시 성공은 아래 다섯 가지 동작과 증거로 판정한다. 방문자 수·전환율처럼 합의되지 않은 사업 지표나 임의의 성능 수치를 추가하지 않는다.

| ID | 성공 기준 | 확인할 증거 |
| --- | --- | --- |
| S-01 | 닉네임 설정 후 같은 브라우저 재방문 시 동일 계정과 닉네임을 유지한다. 같은 닉네임의 다른 계정은 작성 권한을 얻지 못한다. | 독립 익명 세션의 재방문·권한 검증 결과 |
| S-02 | 글·이미지·그림의 비어 있지 않은 7가지 조합을 생성하고, 본인이 구성 요소를 수정·제거할 수 있다. 빈 게시물은 저장하지 않는다. | 각 조합의 저장·재조회, 마지막 콘텐츠 제거 거절 결과 |
| S-03 | 독립 세션 두 개에서 생성·수정·삭제가 새로고침 없이 반영되고, 재연결 후 조회 범위의 내용이 서버와 일치한다. | 실제 배포 URL에서 두 세션의 반영·복구 기록 |
| S-04 | 그림 저장 후 획을 복원해 편집할 수 있고, 업로드·저장 실패나 충돌 시 열려 있는 창의 초안을 보존한다. | 획 복원·실패·충돌 검증 결과 |
| S-05 | Vercel 배포에서 인증·CRUD·Realtime·Storage 정리가 동작하고, 타인 데이터 변경과 방문자의 정리 큐 접근은 거절된다. | 배포 URL, 실행한 검증 결과, 실제 파일 정리 및 거절 요청의 증거 |

정상 연결에서 실시간 변경은 수 초 내 반영을 목표로 한다. 정확한 지연 합격선·동시 접속 규모·부하 시험 데이터 규모는 아직 정하지 않았으며, 아래 기능 검증을 부하·성능 보장의 근거로 사용하지 않는다.

## 2. User Experience & Functionality — 사용자 경험과 기능

### 2.1. 사용자가 정한 내용

- 익명으로 로그인하되 처음 접속했을 때 닉네임을 묻는다. 같은 브라우저에서는 로그인 상태와 닉네임을 유지한다.
- 게시물을 조회·작성하고 자신의 게시물을 수정·삭제할 수 있다. 글·이미지·그림 각각도 추가·수정·삭제할 수 있다.
- 글, 이미지, 그림은 각각 선택 사항이다. 글만, 이미지만, 그림만 있는 게시물과 이들을 조합한 게시물을 모두 지원한다.
- 업로드 이미지는 게시물당 최대 5장이다. 용량을 줄이기 위해 자동 리사이즈·압축하며, 저장 이미지당 최대 1 MiB, 이미지 합계 최대 5 MiB를 기준으로 한다.
- 그림은 PC에서 마우스·펜, 모바일에서 손가락·펜으로 그린다. 저장 후 다시 열어 편집할 수 있다.
- 기본 shadcn/ui 느낌의 흑백 디자인을 사용하고 라이트 테마를 기본으로 한다.
- 중앙의 단일 열 피드를 사용한다. 작성·수정은 별도 창에서 진행한다.
- React, TypeScript, Vite, shadcn/ui, Tailwind CSS를 사용한다. Supabase Auth·PostgreSQL·Realtime·Storage를 연결하고 Vercel에 배포한다.
- 그림은 표시용 이미지와 다시 편집할 획 데이터를 함께 저장한다.
- 파일 정리 큐는 일반 PostgreSQL 테이블로 직접 관리한다. Supabase Queues는 사용하지 않는다.

브라우저의 사이트 데이터를 지우거나 다른 브라우저·기기로 바꾸면 기존 익명 계정에 접근할 수 없다는 제한을 안내한다. 계정 복구·계정 연결은 이번 범위에 포함하지 않는다.

### 2.2. 설계자가 정한 기본값과 입력 제한

다음은 사용자가 개별적으로 요청한 값이 아니라, 작은 첫 버전을 완성하기 위해 제안하는 기본값이다. 구현자는 문서 승인 후 이를 기준으로 작업한다.

| 항목 | 기본값 |
| --- | --- |
| 공개 범위 | 방명록과 게시물의 이미지·그림 미리보기는 링크로 누구나 조회 가능 |
| 닉네임 | 앞뒤 공백 제거 후 2~16자, 중복 허용, 이모지 허용. 글자 수는 Unicode 코드 포인트 기준 |
| 닉네임 변경 | 본인 닉네임을 변경할 수 있음. 이미 작성한 게시물의 표시 이름은 작성 당시 이름 유지 |

| 그림 도구 | 펜, 몇 가지 기본 색, 굵기, 지우개, 실행 취소, 전체 지우기 |
| 그림 용량 | 미리보기 최대 1 MiB, 편집용 획 데이터 최대 512 KiB |

| 미디어 배열 | 이미지 순서를 바꿀 수 있음. 본문 → 이미지 → 그림 순으로 표시 |

| 파일 정리 | 서버용 Edge Function과 예약 실행으로 DB 큐의 삭제 대기 작업 처리 |

사진 압축이 완료되어도 목표 용량에 맞출 수 없으면 해당 파일의 문제를 알려주고 저장하지 않는다. 원본은 별도로 서버에 보관하지 않는다. 그림의 추가 용량까지 포함하면 한 게시물은 이미지 합계 5 MiB 외에 그림 미리보기와 획 데이터가 필요하며, 프로젝트 전체 용량은 별도로 모니터링한다.

#### 입력 경계의 판정

기존 상한을 클라이언트와 서버가 동일하게 해석한다. MiB·KiB는 각각 1,024²·1,024바이트이며, 상한과 같은 값은 허용하고 초과는 거절한다. 1 MiB는 1,048,576바이트, 5 MiB는 5,242,880바이트, 15 MiB는 15,728,640바이트, 512 KiB는 524,288바이트다. 15 MiB는 브라우저에서 처리할 원본의 제한이고, 서버에는 변환 후의 파일 제한을 적용한다.

본문의 1,000자도 닉네임과 동일한 Unicode 코드 포인트 단위로 계산하는 것을 설계자 보강안으로 정한다. 본문의 줄바꿈은 보존하고 공백만 있는지는 별도로 검사한다. 그림 획 데이터의 용량은 직렬화된 UTF-8 데이터의 바이트 수로 계산한다. 그림 미리보기는 이미지 5장·합계 5 MiB에 합산하지 않는다.

#### 추가 제안 — 미확정

계정당 새 게시물 생성 간격을 10초로 제한하는 방안은 설계자가 추가한 제안이며, 사용자가 요청하거나 승인한 요구사항이 아니다. 이번 구현 기준에는 포함하지 않고, 필요할 때 별도로 논의한다.

#### 첫 방문과 닉네임

첫 방문에는 짧은 안내와 닉네임 입력 창을 보여준다. 방문자는 이 창을 닫고 피드를 구경할 수 있으며, 작성하려면 닉네임 입력을 마쳐야 한다. 유효한 닉네임으로 시작을 누르면 익명 로그인을 수행하고 본인 프로필을 만든다. 인증 또는 프로필 저장이 실패하면 완료된 것처럼 닫지 않고 재시도할 수 있게 한다.

이후 방문에서는 유지된 세션으로 본인 프로필을 읽는다. 인증이 만료되어 갱신할 수 없는 경우 새 익명 계정을 자동 생성해 기존 작성 권한을 가진 것처럼 표시하지 않는다. 상태를 알리고 닉네임 설정부터 다시 시작하도록 한다. 프로필만 누락된 경우에는 같은 인증 계정으로 프로필 설정을 재개한다.

상단의 닉네임 메뉴에서 닉네임을 바꿀 수 있다. 복구할 방법이 없는 익명 계정이므로 첫 버전에는 로그아웃 기능을 두지 않는다. 닉네임은 표시용이며 계정 소유권을 판단하는 키로 사용하지 않는다.

#### 중앙 피드

데스크톱은 약 720px 폭의 중앙 피드와 넉넉한 바깥 여백을 사용한다. 모바일에서는 한 열을 유지하고 화면 가장자리 여백을 줄인다. 상단에는 서비스명, 연결 상태, 본인 닉네임 메뉴를 두고 그 아래에 작성 시작 영역을 둔다.

카드에는 닉네임, 작성 시간, 선택한 콘텐츠가 나온다. 수정된 글은 수정 표시를 붙인다. 본인의 게시물에만 수정·삭제 메뉴를 보인다. 긴 글은 줄바꿈을 보존하며, HTML을 해석하지 않고 일반 텍스트로 출력한다. 이미지와 그림 미리보기는 비율을 보존하고 누르면 크게 볼 수 있다.

조회 중, 빈 피드, 조회 실패, 더 불러오는 중을 각각 구분한다. 예시 게시물은 실제 서비스에 자동으로 섞어 넣지 않는다.

#### 작성·수정 창

작성 버튼은 모달을 연다. 모바일에서는 화면에 맞춘 넓은 대화상자와 내부 스크롤을 사용한다. 글 입력, 이미지 추가와 미리보기, 그림 추가 버튼, 취소·저장 버튼을 둔다. 이미지마다 제거·교체·순서 변경을 제공한다. 그림은 미리보기와 다시 그리기·제거를 제공한다.

수정 창은 현재 저장된 콘텐츠로 시작한다. 모든 요소를 개별 변경할 수 있다. 같은 브라우저의 다른 창에서 이미 수정한 경우 버전 충돌을 알리고, 현재 작성 중인 내용을 유지한 채 최신 게시물을 다시 확인할 수 있게 한다. 조용히 다른 창의 수정을 덮어쓰지 않는다.

저장 중에는 중복 제출을 막고 상태를 보여준다. 업로드 또는 저장이 실패하면 초안과 선택한 파일을 현재 창에서 유지한다. 저장 성공 후에만 창을 닫는다. 저장하지 않은 변경이 있을 때 창을 닫으면 버릴지 확인한다. 새로고침·브라우저 종료 후의 초안 복구는 이번 범위에 없다.

#### 그림 편집

그림 도구는 별도 대화상자에서 연다. Pointer Events로 마우스·터치·펜 입력을 통합하고 캔버스 안에서만 브라우저 스크롤 제스처를 막는다. 캔버스 밖에서는 페이지를 스크롤할 수 있어야 한다.

획 좌표는 캔버스 비율에 맞게 저장한다. 화면 크기나 픽셀 밀도가 달라도 같은 그림이 재현되어야 한다. 지우개·펜 굵기·색과 획 순서를 저장하여 다시 열어 편집한다. 실행 취소에는 지우개와 전체 지우기도 포함한다. 그림 창의 완료는 게시물 초안에 반영하는 동작이며, 게시물 저장을 누르기 전까지 서버에 확정하지 않는다.

용량 제한을 넘으면 작업을 없애지 않고 안내한다. 사용자는 획을 줄이거나 그림 저장을 취소할 수 있다. 압력 감지, 레이어, 도형, 텍스트 도구, redo는 첫 버전 범위에 없다.

#### 삭제

게시물 삭제에는 확인 창을 둔다. 서버가 게시물 삭제를 확정하면 피드에서 없애고 미디어 정리를 진행한다. 미디어 정리 재시도가 남아 있더라도 게시물이 다시 나타나지 않게 한다. 삭제된 게시물의 파일은 정리가 끝날 때까지 기존 공개 URL에서 잠시 접근 가능할 수 있으므로, 화면에서 없어진 즉시 물리 파일 삭제까지 완료되었다고 주장하지 않는다.

#### 실패·예외 상황의 사용자 경험

다음은 기존의 초안 보존·충돌 처리 원칙을 구체화한 설계자 보강안이다.

| 상황 | 사용자에게 보여줄 결과 | 보존·재시도 조건 |
| --- | --- | --- |
| 닉네임 검증 또는 프로필 저장 실패 | 입력 문제와 인증·저장 실패를 구분하고 창 안에서 안내 | 닉네임 입력 유지. 인증만 성공했다면 동일 계정으로 프로필 저장 재시도 |
| 이미지 변환·일부 업로드 실패 | 실패한 파일과 단계를 표시하고 게시물 저장 성공으로 처리하지 않음 | 본문·선택 파일·그림 유지. 기존 게시물 연결은 변경하지 않음 |
| 저장 요청 후 응답 유실 | 결과 확인 전에는 성공·실패를 단정하지 않고 확인 중 또는 결과 미확인으로 표시 | 동일 게시물 ID로 저장 결과 확인. 새 ID의 중복 게시물을 만들지 않음 |
| 다른 창의 수정으로 버전 충돌 | 충돌을 알리고 최신 저장 내용 확인·다시 읽기 제공 | 현재 초안 유지. 최신 버전으로 자동 재전송하거나 덮어쓰지 않음 |
| 편집 중 다른 창 또는 운영자가 글 삭제 | 삭제되어 더 이상 수정할 수 없다고 안내 | 초안 유지. 자동으로 새 게시물로 전환하지 않음 |
| 그림 획 데이터 손상·지원하지 않는 포맷 | 재편집할 수 없다는 오류와 현재 미리보기 표시 | 오류를 빈 그림으로 바꾸어 자동 저장하지 않음. 사용자 조작 없이 기존 그림을 제거하지 않음 |
| 피드·더 보기 조회 실패 | 빈 피드와 구분한 오류·재시도 상태 표시 | 이미 읽은 카드 유지. 실패한 페이지의 커서를 앞으로 이동시키지 않음 |

모달은 키보드로 조작 가능해야 한다. 열린 대화상자 안에서 초점을 유지하고 닫힌 뒤 시작 버튼으로 돌려준다. Escape·닫기 버튼·바깥 영역 클릭은 동일한 미저장 변경 확인 규칙을 따른다. 저장 처리 중에는 모달 닫기와 중복 제출을 막는다. 그림 창 취소는 열기 전 게시물 초안의 그림을 유지한다.

### 2.4. 포함하지 않는 기능과 피해야 할 결과

댓글, 좋아요, 검색, 팔로우, 알림 서비스, 소셜·이메일 로그인, 여러 방명록 공간, 비공개 게시물, 자동 콘텐츠 심사, 계정 복구, 다크 모드, 고급 드로잉 도구는 첫 버전 범위 밖이다.

CAPTCHA와 Turnstile 연동은 사용자 요구사항에 없으므로 이번 구현에 포함하지 않는다.

다음 상태는 기능 일부가 작동하더라도 완료로 보지 않는다.

- 새로고침해야 다른 사람의 변경이 보임
- 닉네임만으로 소유권을 판정하거나 남의 게시물·파일을 수정 가능
- 글이 없거나 이미지가 없다는 이유로 유효한 게시물을 저장하지 못함
- 그림을 이미지로만 저장해 재편집할 수 없음
- 업로드 실패인데 저장 성공으로 표시하거나 작성 중 내용을 잃음
- 모바일에서 그림을 그리는 대신 페이지가 움직이거나 저장 버튼이 화면 밖으로 사라짐
- 비밀 키 노출, 관련 없는 프로젝트 변경, 배포 링크만 확인하고 실제 CRUD를 검증하지 않음

## 3. AI System Requirements — 해당 없음

이 제품은 생성형 AI, AI API, 자동 콘텐츠 심사 기능을 사용하지 않는다. AI 도구 요구사항과 모델 평가 전략은 적용 대상이 아니며, 그림 기능은 사용자가 직접 그린 획을 저장·복원하는 기능이다.

## 4. Technical Specifications — 기술 명세

### 4.1. 아키텍처와 연동 경계

작성 흐름은 닉네임·인증 확인 → 초안 편집 → 미디어 준비·업로드 → 게시물 DB 확정 → 카드 반영이다. DB 확정 전 업로드 파일이 존재할 수 있으므로 실패 보상과 만료 정리를 별도로 수행한다. 삭제 흐름은 게시물 삭제·정리 작업 등록을 먼저 확정하고, 예약 작업자가 물리 파일을 나중에 삭제한다.

### 4.2. 데이터와 소유권

데이터 모델은 아래 책임을 지키되 세부 SQL 이름과 보조 테이블은 구현자가 정할 수 있다.

| 데이터 | 주요 내용 | 읽기·쓰기 |
| --- | --- | --- |
| profiles | 인증 UUID, 현재 닉네임, 생성·수정 시간 | 본인만 조회·수정 |
| entries | 게시물 UUID, 작성자 UUID, 작성 당시 닉네임, 본문, 버전, 생성·수정 시간 | 공개 조회, 작성자만 변경 |
| entry_images | 게시물, 이미지 경로·크기·순서·바이트 수 | 공개 조회, 작성자만 변경 |
| entry_drawings | 게시물, 미리보기 경로·크기·바이트 수 | 공개 조회, 작성자만 변경 |
| drawing_strokes | 그림 편집용 데이터, 포맷 버전 | 작성자만 조회·변경 |
| media lifecycle | 업로드 준비 상태, 사용 여부, 삭제 대기 상태 | 본인 업로드 준비만 허용, 정리는 서버 권한 |
| media_cleanup_jobs | 파일 삭제 작업, 처리 상태, 선점 만료, 재시도 정보 | 서버 내부 전용 |

모든 외부 공개 스키마 테이블에 RLS를 적용하고, 필요한 역할의 GRANT도 함께 명시한다. 익명 로그인 사용자도 `authenticated` 역할을 사용한다. 로그인 전 공개 조회에는 `anon` 역할의 명시적인 SELECT 권한을 준다. 익명 사용자와 로그인 전 역할의 차이는 [Supabase 익명 로그인 문서](https://supabase.com/docs/guides/auth/auth-anonymous)를 기준으로 한다.

작성자 UUID는 `auth.uid()`를 기준으로 서버에서 검증한다. INSERT·UPDATE의 소유권, 연결된 게시물 소유권, 관계 이동을 각각 막고 UPDATE에는 USING과 WITH CHECK를 적용한다. 작성 당시 닉네임은 본인의 프로필에서 서버가 가져오며, 클라이언트가 다른 사람의 이름·UUID를 써서 소유자로 가장할 수 없게 한다. SQL·서버 권한을 쓰는 함수는 인증과 소유권을 함수 내부에서 검사하며 실행 권한을 최소화한다.

게시물 저장은 RPC 등 하나의 DB 트랜잭션으로 본문·이미지 목록·그림·획 데이터를 확정한다. 빈 게시물 금지, 이미지 5장, 크기 제한, 이미지 순서, 그림 1개, 버전 비교를 서버에서도 검증한다. 각 요소의 직접 테이블 변경으로 이 검증을 우회하지 못하게 한다. 획 데이터는 게시물 공개 조회와 Realtime 이벤트에 실리지 않도록 분리한다.

#### 저장·재시도·충돌 계약

기존 구현 계획의 게시물 ID 재사용·버전 비교를 제품 동작으로 명시한다. 새 글은 제출 전에 UUID를 만들고 동일 초안의 재시도에서도 유지한다. 같은 ID의 생성 요청이 반복되어도 행은 하나만 존재해야 하며, 기존 글을 신규 생성 요청으로 덮어쓰지 않는다.

응답을 받지 못한 요청은 해당 ID를 재조회해 결과를 확인한다. 존재만으로 현재 초안이 저장되었다고 판단하지 않고 작성자·버전·저장 내용과 요청을 비교한다. 일치하지 않거나 확인 요청도 실패하면 초안을 유지하고 결과 미확인 또는 충돌로 안내한다. 수정·삭제에는 읽은 버전을 보내며, 버전이 바뀌었거나 대상이 없으면 기존 내용을 변경하지 않는다. 요청 식별·오류 코드·비교 구현은 구현자가 정하되, 불확실한 결과를 자동 재전송으로 덮어쓰지 않는다.

미디어 연결·순서·획 데이터·게시물 버전·삭제 작업 등록은 모두 성공하거나 모두 롤백되어야 한다. 검증 실패 후 본문만 바뀌거나 미디어 일부만 교체된 상태는 허용하지 않는다. 사용자에게는 입력 오류·인증 필요·권한 없음·충돌·네트워크/서버 실패를 구분해 안내하고, 원시 DB 오류와 비밀 값은 출력하지 않는다.

### 4.3. 파일 저장과 정리

이미지와 그림 미리보기는 공개 방명록용 Storage 버킷에 저장한다. 공개 URL을 아는 사람이 파일을 볼 수 있다는 안내를 작성 화면에 짧게 제공한다. 비공개 게시물 기능은 제공하지 않는다. 획 데이터는 공개 버킷에 올리지 않는다. 공개 조회와 업로드·삭제 권한의 차이는 [Supabase 공개 버킷 문서](https://supabase.com/docs/guides/storage/buckets/fundamentals#public-buckets)를 기준으로 한다.

파일 경로는 인증 UUID와 게시물 UUID 아래의 고유 파일명으로 구성한다. 서버에서 준비된 업로드 경로만 허용하고, 다른 계정의 경로·게시물에 업로드하거나 삭제할 수 없게 Storage 정책으로 제한한다. 버킷에도 파일 크기와 허용 MIME 제한을 설정한다. 클라이언트가 주장한 크기·경로만 믿지 않고 Storage 메타데이터와 준비된 업로드 레코드를 확인하여 게시물에 연결한다. 제품은 정적 이미지 파일만 제공하며 파일명과 본문을 HTML로 렌더링하지 않는다.

이미지를 바꾸면 기존 경로를 덮어쓰지 않고 새 파일을 올린다. 업로드 완료 후 DB 저장이 성공하면 새 파일을 연결하고 이전 파일을 삭제 대기에 넣는다. DB와 Storage는 하나의 원자적 트랜잭션이 아니므로 실패 시 보상 작업이 필요하다.

- 업로드 중 실패: 게시물은 확정하지 않고 초안을 유지한다. 이미 올라간 파일은 정리 대상으로 남긴다.
- DB 저장 실패: 기존 게시물과 파일 연결을 유지한다. 새 파일은 미사용 상태로 정리한다.
- 수정·삭제 성공: 분리된 파일을 삭제 대기열에 넣어 Storage API로 삭제한다.
- 창 종료 등으로 남은 미사용 업로드: 24시간이 지난 준비 레코드와 파일을 주기적으로 정리한다.
- 정리 실패: 재시도 상태를 기록하고 다음 정리 실행에서 재처리한다. 현재 참조 중인 파일은 삭제하지 않는다.

정리 작업은 서버 권한을 가진 Supabase Edge Function과 예약 실행을 사용한다. 처리 주기와 한 번에 처리할 작업 수는 설정 가능하게 하고 구현 시 기본값을 README에 기록한다. 서비스 키·예약 작업 인증 비밀은 서버 환경에만 둔다. Storage 내부 테이블을 SQL로 지워 파일 삭제를 대신하지 않는다. 본인 파일도 UI에서 직접 삭제하는 대신 게시물 변경과 정리 흐름을 통하게 하여 DB가 참조하는 파일의 갑작스러운 삭제를 막는다.

#### DB 테이블로 관리하는 파일 정리 큐

큐의 저장·선점·완료·재시도 상태는 일반 PostgreSQL 테이블에서 관리한다. Realtime 구독은 큐의 실행 조건이 아니다. 작업자는 예약 실행으로 DB를 조회해 처리할 작업을 가져오며, 방명록 화면의 실시간 반영은 4.4절의 별도 Realtime 구독이 담당한다.

작업자를 깨우는 역할은 Supabase Cron이 맡는다. 정해진 주기에 `pg_net`으로 Edge Function을 호출하고, 함수는 처리 가능한 작업을 제한된 수만큼 선점한다. 반환된 작업이 없으면 종료한다. 작업이 있으면 처리하며, 실행 시간·건수 한도 안에서 다음 작업을 가져온다. 한도를 넘은 나머지는 DB에 남겨 다음 실행에서 이어간다. 전체 작업 수를 먼저 COUNT하거나 일정량이 쌓일 때까지 기다릴 필요는 없다. pending·processing·failed 건수와 가장 오래 기다린 시간은 운영 확인용 지표로 조회한다.

이는 주기적으로 확인하는 polling 방식이다. 새 작업이 추가된 순간 자동 실행되는 것으로 설명하지 않는다. 마지막 조회 직후 등록된 작업도 DB에 보존되고 다음 예약 실행에서 확인한다. 예약 실행이 실패한 경우에도 후속 실행에서 남은 작업을 다시 조회할 수 있다. 처리 주기가 1분이라면 일반적으로 다음 확인까지 최대 약 1분이 걸릴 수 있고, 적체·오류·예약 실행 실패가 있으면 더 오래 걸릴 수 있다. 1분은 설명을 위한 예시이며 확정된 운영값은 아니다.

`media_cleanup_jobs`의 각 행은 파일 하나의 삭제 작업이다. 최소 정보는 다음과 같다. 실제 테이블은 외부에 노출하지 않는 내부 스키마에 두고, 서버 전용 함수로 관리한다.

| 정보 | 용도 |
| --- | --- |
| id, bucket, object_path | 작업과 삭제할 파일 식별 |
| status | pending, processing, done, failed |
| created_at, updated_at, finished_at | 처리 순서와 운영 기록 |
| attempts, next_attempt_at, last_error | 재시도 횟수·다음 시도 시간·최근 실패 원인 |
| claim_token, lease_until | 현재 작업자의 선점 식별과 만료 시간 |

1. **등록:** 게시물 수정·삭제와 파일 삭제 작업 등록을 같은 DB 트랜잭션에서 확정한다. 파일 경로는 서버가 기존 미디어 연결에서 가져온다. 클라이언트가 임의 경로를 큐에 넣을 수 없다. 관리 도구에서 게시물을 삭제하는 경우에도 등록되도록 트리거 등 DB 수준에서 보장한다.
2. **선점:** RPC가 실행 시각이 된 pending 작업을 정렬해 가져오고, `FOR UPDATE SKIP LOCKED`로 잠근 행을 같은 짧은 트랜잭션에서 processing으로 바꾼다. attempts를 증가시키고 새로운 claim_token과 lease_until을 기록한 뒤 커밋한다. 조회와 상태 변경을 별개의 요청으로 나누지 않는다.
3. **실행:** 선점 RPC가 끝난 뒤 Edge Function이 Storage API를 호출한다. 파일 삭제를 기다리는 동안 DB 트랜잭션이나 행 잠금을 유지하지 않는다.
4. **완료:** 파일 삭제에 성공하면 별도 RPC로 done을 기록한다. 작업 ID·claim_token·유효한 선점 상태가 일치할 때만 결과를 반영한다. 완료 기록의 보존 기간은 설정 가능하게 한다.
5. **실패·복구:** 삭제 실패 시 pending으로 돌리고 다음 시도 시간을 늦춘다. 작업자가 중단되어 processing이 남으면 선점 만료 후 다시 가져올 수 있게 한다. 지연 재시도 간격·선점 기간·최대 시도 횟수는 설정값으로 두며, 한도에 도달한 작업은 failed로 남겨 운영자가 확인·재등록할 수 있게 한다. 선점 만료로 한도에 도달한 작업도 방치하지 않고 failed로 정리한다.

#### 파일 삭제 순서: 등록 순서의 FIFO와 재시도 대기

2026-10-14 사용자 요청에 따라 파일 정리 순서는 등록 순서의 FIFO를 기준으로 한다.
현재 처리할 수 있는 작업들 중 큐에 먼저 등록된 작업을 먼저 선택한다.
등록 순서는 작업 행의 `created_at` 오름차순이며, 파일 업로드 시각이나 게시물 작성 시각과는 다르다.

- 새 작업은 등록 후 처리할 수 있다. 실패한 작업은 `next_attempt_at`까지 기다린다.
- `next_attempt_at`은 재시도해도 되는 시각이다. 작업 간 우선순위를 정하는 정렬 값으로 사용하지 않는다.
- 앞 작업의 재시도 시각이 아직 되지 않았다면, 뒤에 등록된 처리 가능한 작업을 먼저 선택한다.
- 재시도 시각이 되면 원래의 `created_at`을 유지한 채 다시 선택 대상이 된다.
  실패할 때마다 새 작업처럼 큐의 맨 뒤로 보내지 않는다.
- 다른 작업자가 선점 중인 작업은 건너뛰며, 선점이 만료된 작업은 다시 처리 대상이 될 수 있다.

예를 들어 A가 10:00에, B가 10:02에 등록됐다고 하자.
A가 삭제에 실패해 10:06까지 재시도를 기다린다면, 10:03에는 B를 처리할 수 있다.
10:06부터 A는 원래 등록 시각인 10:00을 기준으로 다시 선택 대상이 된다.
A를 기다리는 동안 뒤 작업 전체를 멈추지 않는 방식이다.

이 FIFO 기준은 처리 가능한 작업의 선택 순서다. 재시도 대기와 `FOR UPDATE SKIP LOCKED`,
여러 작업자의 처리 시간 차이 때문에 실제 파일 삭제 완료 순서는 달라질 수 있다.
동일한 `created_at`을 가진 작업 사이의 순서도 보장하지 않는다.
독립적인 파일 삭제에는 엄격한 완료 순서가 필요하지 않다.
대기 작업 조회와 만료된 선점 조회에는 상태에 맞춘 인덱스를 둔다.

이 방식의 push는 작업 행 등록에 해당한다. pop처럼 가져오면서 행을 지우지 않고, 선점 → 파일 삭제 → 완료 기록 순서를 지킨다. Storage 삭제 성공 직후 완료 RPC가 실패하면 같은 작업이 다시 실행될 수 있다. 이미 없는 파일은 삭제 목적이 달성된 것으로 처리하고, 같은 경로의 반복 삭제가 다른 파일에 영향을 주지 않게 경로를 재사용하지 않는다. 외부 파일 삭제의 exactly-once 실행을 보장한다고 주장하지 않는다.

동일 bucket·object_path의 중복 등록을 막는다. 큐 행은 게시물 삭제와 함께 cascade로 사라지지 않아야 한다. 삭제 대기로 넘어간 파일을 다시 게시물에 연결하지 못하도록 미디어 상태 전환과 첨부 검증을 같은 DB 레코드 잠금으로 조율한다. 현재 참조가 남아 있는 파일은 삭제하지 않고 작업을 실패 상태로 남겨 확인한다.

큐 테이블과 작업자용 선점·완료·재시도 함수는 anon·authenticated에 직접 노출하지 않는다. 공개 스키마가 불가피하면 RLS와 권한 회수로 같은 제한을 적용한다. 방문자는 본인 게시물 변경 RPC만 호출하며, 임의 작업 생성·조회·완료 처리를 할 수 없다.

### 4.4. 실시간 동기화와 연결 복구

Supabase Postgres Changes로 공개 게시물 변경을 구독한다. 공개 게시물의 변경을 알릴 대상 테이블을 `supabase_realtime` publication에 포함한다. 글·미디어만 바뀐 수정도 entries의 버전·수정 시간을 갱신하여 entry 이벤트 하나로 최신 카드 전체를 다시 조회할 수 있게 한다.

INSERT·UPDATE는 해당 게시물과 공개 미디어 목록을 조회해 UUID 기준으로 추가·교체한다. DELETE는 기본 키로 제거하며 작성자 정보 등 삭제 payload의 다른 필드에 의존하지 않는다. 본인 저장 응답과 구독 이벤트가 중복되어도 카드가 중복되지 않게 한다.

처음에는 구독 준비와 초기 조회를 조율하고 그 사이 도착한 변경을 반영한다. 재연결·탭 복귀 시 현재 조회 범위를 다시 동기화하여 누락된 글, 수정, 삭제를 복구한다. 구독 상태가 연결 완료인지 확인하고, 실패·연결 끊김을 화면에 표시한다. 단순 HTTP 조회 성공이나 `SUBSCRIBED` 로그만으로 실시간 동작을 검증했다고 하지 않는다.

최상단을 보고 있으면 새 글을 바로 표시한다. 아래쪽을 읽고 있으면 스크롤을 갑자기 이동시키지 않고 새 글 알림 버튼을 제공한다. 오래된 게시물을 수정했다고 최신 작성 위치로 끌어올리지 않는다. 더 보기에는 생성 시간과 UUID를 함께 쓰는 안정적인 커서를 사용한다. 자동 동기화가 열려 있는 편집 초안을 덮어쓰지 않게 한다.

연결이 끊긴 동안 입력은 유지한다. 저장이 실패하면 실패를 표시하며, 연결이 돌아왔다고 초안을 자동 제출하지 않는다. 정상적인 연결에서 변경이 다른 브라우저에 수 초 내 보이는 것을 목표로 하며, 네트워크 지연을 숨기거나 즉시 전송을 보장하는 문구는 쓰지 않는다.

#### 이벤트와 조회 응답의 순서

서버의 생성 시간과 UUID를 내림차순 정렬에 함께 사용하고, 더 보기 커서도 같은 기준을 따른다. 동일 ID는 한 카드로 합치며, 이미 반영한 버전보다 오래된 조회 응답이 최신 카드를 덮어쓰지 못하게 한다. 삭제 이벤트 뒤에 도착한 이전 조회 응답도 카드를 되살리지 못하게 한다.

재연결·탭 복귀 시에는 현재 읽은 가장 오래된 커서까지 동기화한다. 첫 20개만 다시 읽고 그 아래의 오래된 카드·삭제를 방치하지 않는다. 아직 불러오지 않은 과거 게시물의 UPDATE 때문에 그 카드를 최신 글 위치에 끼워 넣지 않는다. 연결 표시와 조회 성공은 구분하며, 연결만 복구되고 동기화 조회가 실패한 경우 최신 상태라고 표시하지 않는다.

### 4.5. 배포와 운영 설정

익명 로그인은 닉네임 입력으로 시작한다. 본문 길이·이미지 개수·파일 용량 등 문서에 정한 입력 제한은 서버에서도 검증한다.

기존 공개 Supabase 프로젝트를 임의로 재사용하지 않는다. 기존 설계에서 언급한 `calendar-app`은 이번 방명록의 배포 대상으로 선택된 적이 없다. **별도의 방명록 전용 Supabase 프로젝트를 권장하며, 기존 설계 작성 시에는 생성·연결되지 않은 상태였다.** 이번 문서 보강에서는 연결 상태를 다시 조회하지 않았으므로 실제 대상과 연결 여부는 구현 준비 시 확인한다. 실제 계정·조직·리전·요금제와 Vercel 배포 대상도 확인할 운영 설정이다. 유료 요금제를 임의 선택하거나 기존 서비스의 DB를 변경하지 않는다.

개발 환경과 배포 환경의 URL·공개 키를 환경 변수로 관리한다. 프런트에는 Supabase 공개 키만 사용하고 비밀 키를 넣지 않는다. Supabase Auth의 허용 URL과 Vercel의 환경 변수를 실제 배포 URL에 맞춘다. `.env.example`은 변수명과 안내만 제공한다.

첫 버전에는 별도의 관리자 화면·신고 기능을 만들지 않는다. 운영자는 Supabase 관리 도구를 사용해 부적절한 게시물을 정리할 수 있으며, 이때도 미디어 삭제 흐름이 실행되도록 DB 삭제 시 정리 대상을 남긴다. Storage·DB 사용량과 정리 실패를 확인할 수 있도록 운영 설명서를 남긴다. 무료 또는 무제한 운영이 가능하다고 단정하지 않는다.

### 4.6. 구현자에게 맡기는 결정

문서의 사용자 경험·권한·상한·실시간 복구 조건을 지키는 범위에서 폴더 구조, 상태 관리 방식, UI 아이콘, 폰트, 구체적인 간격, SQL 함수·보조 테이블 이름, 큐의 처리 주기·선점 기간·재시도 간격·최대 시도 횟수·완료 기록 보존 기간, 이미지 압축 단계, 획 포맷의 내부 구조는 구현자가 정한다. CSS 클래스는 기본적으로 BEM 이름을 사용하되 shadcn/Tailwind의 유틸리티 클래스 사용을 막지는 않는다.

DB 변경은 버전 관리되는 마이그레이션으로 남기고, Supabase 의존성은 버전을 고정하고 lockfile을 포함한다. 현재 임시 프로토타입 파일을 실제 앱 소스로 그대로 승격하지 않는다. 제품은 승인된 구성으로 새로 작성한다.

디자인 기준은 이미 선택한 중앙 피드형 B다. 임시 시안은 `.superpowers/brainstorm/144-1791749620/content/layout-options-v2.html`에 있으며 이 디렉터리는 Git에서 제외된다. 임시 서버 URL·접근 키나 시안의 예시 데이터를 배포 설정에 넣지 않는다.

### 4.7. 검증과 인도 기준

구현 시 의미 있는 범위로 타입 검사·프로덕션 빌드를 수행하고, 권한·저장 트랜잭션·충돌 처리처럼 잘못되면 사용자 데이터에 영향을 주는 로직을 검증한다. 단순 스타일·클릭 동작을 구현과 똑같이 복제하는 테스트는 만들지 않는다.

배포 환경에서 서로 다른 익명 계정을 가진 독립 브라우저 세션 두 개로 다음을 확인한다.

1. 닉네임 설정과 같은 브라우저 재방문 유지. 동일 닉네임의 다른 계정도 소유권은 다름.
2. 글만·이미지만·그림만·혼합 게시물 생성. 다른 세션에서 새로고침 없이 표시.
3. 본인 글·이미지 교체/순서 변경/제거·그림 재편집/제거. 다른 세션에서 수정 반영.
4. 마지막 콘텐츠 제거 후 빈 저장 차단, 이미지 6장·크기 초과·잘못된 형식 차단.
5. 게시물 삭제의 실시간 반영 및 Storage API를 통한 실제 파일 정리. 실패한 업로드의 정리 실행 확인.
6. UI를 우회한 다른 계정의 DB 수정·삭제·관련 데이터 변경·Storage 업로드/삭제 요청 거절. 공개 조회 권한은 유지.
7. 연결 끊김과 재연결 후 누락·중복·삭제 복구, 입력 초안 유지, 같은 글 동시 수정의 충돌 안내.
8. PC 마우스와 모바일 터치 입력, 획 복원, 지우개·취소·전체 지우기. 실제 기기 펜 검증을 못 했다면 미검증으로 명시.
9. 데스크톱과 390px·320px 폭 모바일에서 가로 넘침 없이 읽기·작성·그림 편집. 키보드 초점, 대화상자 닫기, 버튼 레이블 확인.
10. 실제 Vercel URL에서 새로고침·인증·CRUD·Realtime·Storage를 확인하고 브라우저 오류를 점검.

DB 큐는 추가로 다음을 검증한다. Realtime 구독을 하지 않은 작업자도 동작해야 한다. 작업자 두 개의 동시 선점에서 유효한 선점이 중복되지 않는지, 게시물 트랜잭션 롤백 시 삭제 작업도 남지 않는지, 작업자 중단 후 선점 만료로 복구되는지, 파일 삭제 성공 후 완료 기록 실패를 안전하게 재처리하는지 확인한다. 오래된 claim_token으로 결과를 덮어쓸 수 없어야 하며, 최대 시도 횟수에 도달한 작업은 failed로 확인 가능해야 한다. 방문자의 큐 직접 접근·임의 파일 삭제 작업 등록도 거절되어야 한다.

인도물은 앱 소스, DB 마이그레이션·정책·정리 작업, 환경 변수 예시, 개발·배포·운영 README, 실제 배포 URL과 검증 결과다. 미연결 서비스나 검증하지 못한 동작은 완료로 포장하지 않고 구분한다.

### 5.4. 설계 검토와 승인 이력

2026-10-11에 대화 내용을 넘겨받지 않은 별도 검토자가 문서를 읽고, 구현 계획을 세우려면 반드시 필요한 결정이 빠졌는지 확인했다. 결과는 `nothing important left`였다. 이는 구현·보안·배포 검증 완료를 뜻하지 않는다.

이후 사용자 검토에서 요구사항에 없던 CAPTCHA 연동을 제거했다. 계정별 생성 간격 제한도 미확정 제안으로 분리하고 이번 구현 기준에서 제외했다.

사용자가 일반 DB 테이블로 큐를 직접 관리하는 방식을 선택하여 파일 정리 큐의 저장·선점·재시도·완료 흐름을 구체화했다. 큐 실행에는 Realtime 구독이 필요하지 않으며, 실제 Storage 삭제는 DB 트랜잭션 밖에서 수행한다.

구체화한 DB 큐 설계도 별도 검토자가 읽었으며, 구현 계획에 꼭 필요한 미결정 사항은 없다는 결과를 받았다. 이는 설계 검토 결과이며 실제 동시성·장애 복구 테스트 결과는 아니다.

2026-10-14 사용자가 먼저 등록된 삭제 작업을 우선하는 FIFO 기준을 선택하고 설명 추가를 요청했다.
이에 따라 기존의 다음 시도 시각 우선 정렬 설명을 등록 순서 기준으로 바꿨다.
재시도 대기 중 뒤 작업을 처리하는 예외를 명시했으며 제품 코드와 DB 구조는 변경하지 않았다.

사용자는 문서를 읽고 질의한 뒤, 2026-10-11에 전체 설계를 최종안으로 확정하고 구현 계획 작성 단계로 진행하는 데 승인했다. 미확정 제안으로 분리한 생성 간격 제한은 승인 범위에 포함하지 않는다.
